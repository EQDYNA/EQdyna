# v5.20.2 retag, 2026-09-30

**Old tag/Release: `v5.20.2` -> `30ae29e6b780ad48bd185e10b75808b8f3162eab` (RED, replaced). New tag/Release: `v5.20.2` -> `4b5da1c30637ebddaf1124dc1a0c7d58bd1076b6` (GREEN).**

## What was wrong with `30ae29e`

`30ae29e` is a docs-only commit (`docs/evidence/sweep-e0c407f/summary.json`
and friends), then covered by `test.yml`'s blanket `docs/**` paths-ignore, so
it could never trigger its own push-run. The pre-tag gate
(`check_pretag_ci.py --ack-paths-ignored-parent`) accepted its parent
(`e0c407f`)'s green run as evidence instead, and the tag was cut on that
basis. `test.yml`'s own comment already said paths-ignore is not evaluated
for tag pushes, so pushing the `v5.20.2` tag DID trigger a real, full CI run
against `30ae29e` itself -- and it failed at `test_term_axis.py`, because the
fix for that test (`850ce6a`, PR #68) postdates `30ae29e`. Separately, the
Docker image workflow never had a green run for `30ae29e` at all (it only
triggers on tag push / `workflow_dispatch`, and the tag-push run's own
`test.yml` gate failed before the image build step, per this repo's own
in-image gate design), so `docker pull ghcr.io/eqdyna/eqdyna:v5.20.2` 404'd.

## The fix

Two PRs, landed in order, before this retag:

- **PR #69** (`ff06534`): `check_pretag_ci.py`/`ci_status.py` hardened so a
  tag only goes on a SHA with its OWN completed, green CI run --
  `--ack-paths-ignored-parent` no longer authorizes a PASS from an
  ancestor's run under any circumstance. New `IMAGE_WORKFLOW_NOT_READY`
  (exit 7): a tag also requires `publish.yml`'s own green run for the exact
  SHA, not just "if it ran, it was green." `test.yml`'s paths-ignore
  narrowed so evidence/ledger paths a test reads are no longer misclassified
  as inert docs (rule 15g). `PROJECT_RULES.md` rules 15a/15g/24/24a.
- **PR #70** (`4b5da1c`): landing PR #69 exposed a second defect --
  squash-merging a PR that bundles code with matching `PROJECT_RULES.md`
  text (and, in that PR, a `pathway_forward.md` row) flattens them into ONE
  commit on master, which `check_board_separation.py`'s then-per-commit-only
  check could not see coming from the PR's own (individually clean) commits.
  Fixed: `PROJECT_RULES.md` may now share a commit with its own enforcing
  code (`pathway_forward.md` still may not, unconditionally); `--squash-check`
  is now the sole gating check for `pull_request` CI events, judging the
  PR by the ONE diff a squash-merge will actually produce (three-dot,
  merge-base, not two-dot -- a victor-reyes audit finding, fixed same PR);
  `ff06534` recorded as a one-time named exemption. `PROJECT_RULES.md` rule
  21c.
